# Internationalization

`@ken/locales` owns locale support and every app-authored message. Base
`en.json` is US English and complete; region files contain overrides only.

Expo uses i18next and detects the device locale once at startup through
`apps/expo/src/locale/utils.ts`. No other module may import
`expo-localization`. Next.js uses next-intl but is fixed to `en-US`, keeping the
current site statically renderable. Add locale-prefixed routes or request
detection only when the web app gains another language.

## Adding locales

To add a region for an existing language:

1. Add a partial lowercase `<language>-<region>.json` override in
   `packages/locales/src/`.
2. Register its IETF tag and fallback in `SUPPORTED_LOCALES`.
3. Import the override in `messages.ts` and in Expo's i18next resources.
4. Extend the backend push-token validator if notifications support it.

To add another language in a region:

1. Add a complete base-language catalogue with the same keys as `en.json`.
2. Add each supported language-region tag and fallback, then register its
   regional overrides in both message adapters.
3. Add the matching Clerk web localization before enabling that locale on web.

`SUPPORTED_REGIONS` and locale/region types derive from `SUPPORTED_LOCALES`;
do not maintain separate type unions.

## Message boundaries

Keys are kebab-case and nested by platform or shared area, feature, then
element. Use `shared` only for plain strings: next-intl uses ICU placeholders,
while i18next uses `{{variable}}`. Interpolated and pluralized messages belong
under `web` or `mobile` unless both adapters can consume the exact syntax.

Components translate at render time. Lookup tables carry typed keys, not
rendered strings. Backend-authored notifications use the locale stored with
each device token; missing legacy values fall back to `en-US`.

Root crash boundaries read default catalogue values directly because they may
render outside their normal provider. Tests assert rendered English copy, not
translation keys.
